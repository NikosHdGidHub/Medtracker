# Настройка Firebase с нуля

## 1. Создание проекта

Откройте [Firebase Console](https://console.firebase.google.com/), нажмите «Создать проект» и задайте название, например Medtracker. Запишите Project ID из настроек проекта. В разделе плана оставьте Spark. Google Analytics приложению не нужен. Для разработки, проверок безопасности и реальных данных лучше использовать разные проекты.

## 2. Регистрация Web App

В обзоре проекта нажмите значок Web `</>` или откройте «Настройки проекта → Ваши приложения → Добавить приложение». Задайте имя веб-приложения. Firebase Hosting включать не требуется. Скопируйте объект `firebaseConfig` для веб-SDK. Поля `apiKey`, `authDomain`, `projectId` и `appId` обязательны. `messagingSenderId` можно перенести для полноты конфигурации. Storage и Analytics не используются.

## 3. Authentication

В разделе «Build → Authentication» нажмите Get started. Вкладка Sign-in method содержит поставщика Email/Password. Включите обычный вход по email и паролю. В «Settings → Authorized domains» добавьте `nikoshdgidhub.github.io` и для разработки `localhost`, если его нет. Указывайте только имена, без схемы и пути. Шаблоны писем доступны в Authentication → Templates.

После запуска зарегистрируйте тестовый аккаунт и найдите его на вкладке Users. При сбросе пароля приложение вызывает стандартный отправитель Firebase. Ссылка из письма ведёт в обработчик Firebase, где пользователь вводит новый пароль. Проверьте фактическое получение письма, включая папку «Спам».

## 4. Cloud Firestore

В «Build → Firestore Database» нажмите Create database. Выберите Standard edition и базу `(default)`. Выберите подходящий регион с учётом задержки, доступности и требований к месту хранения данных. Местоположение базы задаётся при создании. Начните в Production mode.

Вкладка Rules позволяет вставить `firestore.rules` и нажать Publish. Для правил и составных индексов удобна команда из корня репозитория:

```bash
npx firebase login
npx firebase deploy --only firestore:rules,firestore:indexes --project medtracker-156e8
```

Используйте учётную запись владельца целевого проекта. На вкладке Indexes дождитесь готовности индексов. На вкладке Data создайте коллекцию `access` при добавлении первого пользователя. Коллекции под `users/{UID}` создаются при первом допущенном входе и последующих операциях приложения. Родительский документ `users/{UID}` может выглядеть как отсутствующий документ при наличии подколлекций.

## 5. Допуск пользователей

1. При включённой форме регистрации пользователь создаёт аккаунт на странице входа.
2. На экране ожидания он копирует UID и передаёт его владельцу.
3. Владелец сверяет UID и email в Authentication → Users.
4. В Firestore Data создайте документ `access/{UID}`. Имя документа равно UID, а поле `enabled` имеет тип boolean и значение `true`. Строка `"true"` не подходит.
5. Страница ожидания обновится после получения допуска. После входа появится пустой список без тестовых препаратов.
6. Для отзыва доступа измените `enabled` на `false`. При необходимости отключите аккаунт также в Authentication.

После добавления участников можно скрыть форму регистрации значением `VITE_ALLOW_REGISTRATION=false` и пересборкой. Это настройка интерфейса. Контроль доступа к документам остаётся за Rules. Новые Firebase Auth аккаунты, полученные через публичный интерфейс поставщика Identity Toolkit, не получают доступа без отдельного разрешения владельца.

## 6. Локальная конфигурация

Скопируйте `.env.example` в игнорируемый Git файл `.env.local`. Подставьте значения из Web App:

```dotenv
VITE_FIREBASE_API_KEY=your_web_api_key
VITE_FIREBASE_AUTH_DOMAIN=your-project.firebaseapp.com
VITE_FIREBASE_PROJECT_ID=your-project
VITE_FIREBASE_APP_ID=1:123456789:web:example
VITE_FIREBASE_MESSAGING_SENDER_ID=123456789
VITE_ALLOW_REGISTRATION=true
```

Это публичные параметры веб-SDK. Секреты сервисных аккаунтов, пароли и административные токены остаются вне Git, GitHub Pages, переменных Vite и артефактов сборки. После изменений перезапустите Vite. Для production укажите тот же набор в [Actions Variables](deployment.md#настройка-github).

## 7. Первый запуск

```bash
npm ci
npm run dev
```

Откройте адрес из Vite с путём `/Medtracker/`. Войдите под допущенным аккаунтом и добавьте тестовый препарат. Подтвердите слот текущего дня. Проверьте баланс, историю и наличие документов в Firestore. Обновите страницу и войдите в том же аккаунте в другом профиле браузера. Проверка должна показать ту же отметку и остаток.

## 8. Проверка безопасности

Создайте два синтетических аккаунта. Для первого выдайте допуск и создайте запись. Для второго сначала проверьте экран ожидания, затем выдайте допуск и убедитесь, что его журнал пуст. Выйдите и снова переключитесь между аккаунтами. Отзовите допуск первого во время сеанса и проверьте возврат на экран ожидания. Проверки прямого чтения, изменения и подмены владельца описаны в [тестах Rules](testing.md).

## 9. Возможные ошибки

| Симптом | Действие |
| --- | --- |
| `auth/unauthorized-domain` | Добавьте точное имя используемого хоста в Authorized domains. |
| `auth/invalid-api-key` | Заново скопируйте Web SDK API key, проверьте проект и пересоберите. |
| `auth/invalid-credential` | Проверьте аккаунт, Email/Password provider и используемый проект. При необходимости сбросьте пароль. |
| `permission-denied` | Сверьте UID, путь и тип `enabled`. Убедитесь, что опубликованы подготовленные правила для базы `(default)`. |
| Индекс отсутствует | Разверните `firestore.indexes.json` в нужном проекте и дождитесь завершения построения. |
| Нет конфигурации | Проверьте обязательные `VITE_FIREBASE_*` в `.env.local` или Actions Variables. Перезапустите dev-сервер или запустите сборку. |
| Неверный путь Pages | Откройте `/Medtracker/` с заглавной M и обновите опубликованную сборку. |
| JS или CSS возвращают 404 | Проверьте Network, базовый путь Vite и артефакт `dist`. Устаревший Service Worker можно удалить в панели Application браузера. |
| Уведомление не появилось | Включите напоминания в настройках и разрешение сайта в браузере. Проверьте тестовую кнопку и дождитесь дедлайна при открытой вкладке. |
