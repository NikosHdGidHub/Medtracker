# Архитектура и работа с данными

## Компоненты приложения

React управляет защищёнными экранами с hash-маршрутами `#/today`, `#/meds`, `#/history`, `#/reports`, `#/settings`. Состояния Firebase Auth и собственного документа допуска проверяются до подключения слушателей личных данных. Поддерево React привязано к UID. Выход или отзыв разрешения снимает подписки и удаляет данные из интерфейса.

`src/domain` хранит модели, календарные расчёты, генерацию планов, статистику и вычисление окна напоминаний. `src/services/tracker.ts` отвечает за ограниченные запросы, транзакции, аудит, запасы и экспорт. Компоненты принимают данные от сервисного слоя. Firebase SDK хранит локальное состояние сессии штатным способом. Firestore использует стандартный кэш в памяти. После новой загрузки медицинские данные читаются только после проверки допуска сервером. При потере связи отключается редактирование. Изменения считаются выполненными после подтверждения транзакции.

## Вычисление и запись

План вычисляется для выбранного интервала по версиям расписания и календаря, с учётом пауз и завершения курса. Уже наступившие события при правке расписания сохраняются, будущие строятся из новой версии. Если один слот попадает в две версии на одной логической дате, выбирается первая наступившая версия. Маркер факта сохраняет полный снимок плана, в том числе при досрочном подтверждении перед сменой расписания.

При обновлении отметки одна транзакция читает актуальную ревизию, записывает факт, аудит и компенсирующее движение запаса. Повторное быстрое подтверждение завершённого слота не списывает запас снова. При конфликте ревизий карточку нужно открыть заново. Запись о приёме не меняет логический день при редактировании фактического времени.

Таймер работает в открытой вкладке, сверяет часы при возврате фокуса, видимости и сети. Состояние попыток хранится локально по UID и техническому идентификатору слота. Web Locks при поддержке браузером координирует вкладки одного устройства. Устройства могут напомнить независимо. Service Worker показывает уведомления по запросу вкладки и хранит только статический список файлов сборки. В кэш Service Worker не входят Firebase API, учётные данные и результаты запросов.

## Приватность и границы доверия

Параметры Firebase Web SDK в клиентской сборке общедоступны. Права доступа проверяют Firestore Rules, а владелец Firebase Console имеет административный доступ к базе. Правила проверяют UID, допуск, основные формы документов, неизменность снимков плановых записей и наличие связанных движений для изменения запасов. Пользователь с изменённым клиентом может создавать собственные синтаксически допустимые записи. Модель клиентского аудита не обеспечивает доказуемость фактов, точность часов или полноту журнала против злонамеренного клиента. Firebase Auth Email/Password и пароль обслуживаются Firebase Authentication.

GitHub Pages обслуживает код и статические файлы. Код, артефакты и логи должны содержать только публичные настройки и синтетические примеры. Официальные ограничения Pages по чувствительным операциям разобраны в [инструкции публикации](deployment.md#ограничения-хостинга).

## Резервирование

В «Настройках» экспорт JSON читает пользовательские коллекции постранично. Это переносимая копия записей и версий расписания, без паролей. Экспорт идёт последовательными запросами, поэтому для согласованной резервной копии удобно временно прекратить редактирование на других устройствах. Импорт через интерфейс в текущей версии отсутствует. CSV можно сохранить из истории за месяц или из отфильтрованного отчёта. Храните экспорт в защищённом месте и исключите его из Git, публичных ссылок и логов.

## Удаление данных

1. Пользователь при необходимости выгружает резервную копию, открывает «Настройки → Удаление данных» и подтверждает запрос.
2. Пользователь передаёт владельцу UID. Владелец сверяет UID с аккаунтом Firebase Authentication и записью `users/{uid}/deletion/main`.
3. Владелец устанавливает `access/{uid}.enabled = false`, затем отключает аккаунт в Authentication, чтобы остановить новые операции.
4. Из доверенной административной среды владелец выполняет `npx firebase firestore:delete "users/<UID>" --recursive --project <PROJECT_ID>`, проверив UID, проект и приглашение CLI. Рекурсивное удаление необратимо и удаляет подвложенные документы. Удаление одного родительского документа через API недостаточно.
5. Владелец удаляет `access/{uid}` из Firestore и соответствующий аккаунт из Firebase Authentication, затем проверяет отсутствие документов и закрывает запрос.

Удаление записи Auth и данных Firestore — отдельные операции. Уже выгруженные файлы пользователь удаляет из своих хранилищ самостоятельно.
